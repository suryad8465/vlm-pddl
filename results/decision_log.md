# Phase 1 Decision Log

## Project
VLM → PDDL → Fast Downward household planning pipeline

## Purpose

This decision log records the main design and implementation decisions
made during Phase 1 of the dissertation project.

---

## Decision 1 — Use a fixed PDDL domain

The PDDL domain is kept fixed while the VLM generates only the problem
file.

This separates the planning model from the VLM output and allows the
generated problems to be tested consistently using Fast Downward.

---

## Decision 2 — Add location update to `putdown`

Initially, the `putdown` action placed an object on a surface but did
not update the object's location.

This made goals such as:

    (located mug living_room)

unreachable after placing the mug.

The `putdown` action was therefore changed to add:

    (located ?o ?l)

to its effects.

This ensures that the object's location is updated when it is placed
on a surface.

---

## Decision 3 — Require the destination surface to be at the same location

After updating `putdown`, the planner found an incorrect solution in
which the mug was placed on the kettle in the living room even though
the kettle was actually in the kitchen.

The `putdown` preconditions were therefore changed to require:

    (located ?s ?l)

This ensures that a surface can only be used for placement when that
surface is actually at the robot's current location.

---

## Decision 4 — Add `place-at-location`

The PyBullet scene contains a table in the kitchen but no table in the
living room.

The task:

    bring the mug to the living room

does not require the mug to be placed on a table. It only requires the
mug to reach the living room.

A separate action, `place-at-location`, was therefore added. This allows
a manipulable object to be released at a destination location without
requiring a surface.

This represents the existing scene without inventing additional
furniture.

---

## Decision 5 — Do not add a living-room table

A living-room table was deliberately not added to the PDDL domain or
scene.

The actual PyBullet scene contains only one table, and that table is in
the kitchen.

Adding another table would make the symbolic representation
inconsistent with the visual scene and could hide errors in the VLM's
scene understanding.

---

## Decision 6 — Strengthen the VLM prompt

The VLM prompt was strengthened to require:

- faithful representation of the scene
- preservation of the complete user task
- no invented objects or locations
- no invented connections
- use of only predicates and actions from the fixed domain
- preservation of requested destinations
- explicit distinction between a location and a destination surface
- syntactically valid PDDL
- a complete `(define ...)` problem structure

The purpose was to reduce hallucinated scene elements, task
simplification, and malformed PDDL.

---

## Decision 7 — Use Fast Downward for Phase 1 planning validation

Fast Downward was selected as the planner for Phase 1.

The generated PDDL problem is passed to Fast Downward after VLM
generation. The planner output is saved together with the generated
problem so that both successful and failed cases can be inspected.

---

## Decision 8 — Include multiple VLM failure cases

Phase 1 includes several different failure modes rather than testing
only successful plans.

The saved experiments include:

1. A working VLM-generated problem with a valid plan.
2. A syntax-error case where the generated PDDL could not be parsed.
3. A hallucinated-location case where the VLM introduced a bedroom that
   was not present in the scene.
4. A task-misinterpretation case where the requested destination was
   changed.
5. A genuine unsolvable case involving an attempt to move the table.

This allows the pipeline to be evaluated for both successful planning
and different types of VLM-generated errors.

---

## Decision 9 — Use a genuine unsolvable case

The task:

    move the table to the living room

was used to test genuine planner-level unsolvability.

The VLM generated a valid PDDL problem containing:

    (located table kitchen)

as an initial fact and:

    (located table living-room)

as the goal.

The table was not marked as manipulable, and the fixed domain contains
no action capable of moving it.

Fast Downward therefore reported:

    No relaxed solution! Generating unsolvable task...

and:

    Task is provably unsolvable.

This case was generated by the normal VLM → PDDL → planner pipeline and
was not manually modified to make it unsolvable.

---

## Phase 1 Conclusion

The Phase 1 pipeline successfully demonstrates:

    Image
      ↓
    VLM
      ↓
    Generated PDDL problem
      ↓
    Fast Downward
      ↓
    Plan / detected failure

The experiments demonstrate both successful planning and several
important failure modes in VLM-generated PDDL.
